## One-line summary

A new host-only crate `codeless-plugin-host-wasm` loads `.wasm`
artifacts via Wasmtime + WASI-preview-2 (the component model),
exposes the same `register_tool(...)` registry seam as builtin
plugins, and enforces fuel + memory + capability caps at the WASI
boundary. Plugin authors write a `ToolBehavior` impl in Rust (or any
WASI-p2 component-model language) and build with
`cargo build --target wasm32-wasip2`.

## Why a component-model host, not core WASM

Two real choices, one obvious answer:

- **Core WASM** (`wasm32-unknown-unknown`, raw ABI). Smallest host
  surface, no toolchain assumption beyond `rustc`. Authors hand-write
  the FFI envelope (rubix's `extensions-sdk/src/wasm.rs` is exactly
  this). Each new I/O shape (attachments, structured results, errors
  with backtraces) is more handwritten marshalling.
- **WASI-p2 component model** (`wasm32-wasip2`). Typed interfaces
  declared in WIT (`tool.wit`), bindings generated by `wit-bindgen`,
  capability handles (filesystem, http, sockets) gated by host policy
  per-instance. Slightly heavier host (`wasmtime` + `wasmtime-wasi` +
  `wit-bindgen-rt`), but the I/O envelope is the WIT contract — no
  pack/leak/read\_slice gymnastics in the SDK, no JSON-as-strings
  inside JSON.

Pick **component model**. The reason rubix's `wasm.rs` is 187 LoC of
unsafe-at-the-FFI-boundary is that core WASM forces the SDK to be the
serialisation layer. We have one chance to pick this; pick the one
that scales as plugin I/O grows.

Cost paid: the WASI-p2 toolchain pins `rustc` ≥ 1.78 (already
codeless's MSRV per [`../../codeless/CLAUDE.md`](../../codeless/CLAUDE.md))
and `wasmtime` 23+. Cost avoided: writing our own typed-FFI
generator, or maintaining a hand-rolled core-WASM ABI as the tool
trait grows.

## The crate

New host-only crate: `codeless-plugin-host-wasm`.

**Mobile-safety:** `codeless-plugin-host-wasm` is host-only. The
mobile shell (`codeless-tauri-mobile`, Phase 6) does not depend on
it. WASM artefacts themselves are portable; a future mobile shell
that wants in-app plugins can ship a `codeless-plugin-host-wasm-
mobile` variant that omits the host capabilities (`fs`, `http`) and
runs trusted plugins only. That is a future decision, not a present
one — but the crate split deliberately allows it.

**Dependency direction:**

```
codeless-server (host-only)
  └─ codeless-plugin-host-wasm (host-only) ──> wasmtime, wasmtime-wasi
       └─ codeless-tools (registry seam; mobile-safe today, host-only
                          once it grows a runtime adapter table — see
                          OQ-WASM-1)
            └─ codeless-types
```

The host crate exports two things:

```rust
pub struct WasmRuntime { /* engine, linker, default limits */ }
pub struct WasmPlugin   { /* a single loaded .wasm + its WIT bindings */ }
```

`WasmRuntime` is created once per server process. `WasmPlugin::load`
is called by `PluginRegistry::load_plugin` (item 6) for every plugin
whose manifest declares a `wasm` runtime entry.

## The WIT contract — `tool.wit`

The interface every WASM tool implements. Versioned with the crate;
breaking changes require a new package version and a
[`PLUGIN-WASM-V2.md`](#) successor doc.

```wit
package codeless:tool@0.1.0;

interface tool {
    record tool-manifest {
        id:             string,
        description:    string,
        input-schema:   string,      // JSON schema serialised
        output-schema:  string,
        tier:           tier,
    }

    enum tier { read, write, destructive }

    record tool-call {
        tool-id:   string,
        args-json: string,           // JSON value serialised
        thread-id: string,           // for attachment scoping (item 7)
    }

    variant tool-result {
        ok(string),                  // JSON value serialised
        err(tool-error),
    }

    record tool-error {
        code:    string,
        message: string,
        retryable: bool,
    }

    // Identity + manifests for every tool the plugin contributes.
    describe: func() -> list<tool-manifest>;

    // Synchronous tool invocation. Long-running tools should split
    // into smaller calls or use the streaming interface (later).
    call: func(req: tool-call) -> tool-result;
}

world plugin {
    export tool;
    import wasi:filesystem/types@0.2.0;    // optional, capability-gated
    import wasi:http/outgoing-handler@0.2.0;
    import wasi:clocks/wall-clock@0.2.0;
}
```

**Why no `subscribe` / streaming RPC in v0.1.** Codeless tools are
synchronous request/response from the agent's POV; the streaming
*event* shape (action card → confirmation → result) lives in the
runtime, not the plugin. If a plugin needs to push events back into
the thread (e.g. progress on a long render), the path is
`ToolCtx::emit_progress(...)` in v0.2, not a WIT streaming RPC. We
add that when a real plugin asks for it.

**Why `args-json: string` and not `args: list<u8>`.** JSON values
crossing the WIT boundary stay as strings. Tools already validate
against a JSON schema; the wire format matches the validator. Binary
attachments cross by `attachment-id` (item 7), not by inlining bytes.

## Capability sandbox — WASI default-deny

By default a loaded plugin sees:

- **No filesystem.** `wasi:filesystem` is *not* linked.
- **No network.** `wasi:http`, `wasi:sockets` are not linked.
- **No clock that returns real time.** `wasi:clocks/monotonic-clock`
  is linked (zeroed at instance boot, used for cooperative yield);
  `wasi:clocks/wall-clock` is *not* linked unless explicitly granted.
- **No env, no args, no stdout/stderr.** WASI stdio is wired to
  capture buffers; anything the plugin writes goes to the plugin's
  log line in the runtime event stream, never to the host process's
  stdio.

Manifest grant syntax (extends item 6's `plugin.toml`):

```toml
[[runtimes]]
kind         = "wasm"
artefact     = "wasm/notes.wasm"

[runtimes.capabilities]
fs           = []                                # no filesystem access
http         = []                                # no outbound http
wall_clock   = false
attachments  = ["read", "write"]                 # codeless-specific
```

**Codeless-specific capability: `attachments`.** Two values,
`"read"` and `"write"`. `read` gives the plugin a host-implemented
WIT interface `codeless:attachments/store@0.1.0` that resolves an
`attachment-id` from the current thread to a byte stream;
`write` lets the plugin mint a new attachment from a byte stream and
return its id from a `tool-result`. This is the typed analogue of
PLUGIN-SUBSTRATE item 7 — same on-the-wire `attachment_id`, but a
WIT interface instead of a raw JSON contract. Plugins **never**
touch `wasi:filesystem` for attachment I/O; that would defeat the
sandbox.

**Why these defaults.** R5 is single-tenant trust, but the blast
radius of a misbehaving WASM tool is still the codeless server's
host process. Default-deny keeps the worst case to "the plugin runs
a hot loop and gets killed by the fuel cap." Anything broader has to
be granted explicitly in the manifest, reviewed by a human.

## Limits — fuel, memory, time

Three caps, all per-call. Configured in `HostPolicy` (codeless-side,
not in the plugin manifest — the plugin doesn't get to set its own
limits).

| Limit | Default | Rationale |
|---|---|---|
| Fuel (Wasmtime "fuel") | 100M units (~100ms wall-clock on modern hardware for compute-bound code) | Wasmtime's primary defence against infinite loops. Refilled per `call()`. |
| Linear memory | 64 MiB | A tool that needs more is probably not a tool. PDF rendering goes via `attachments.write` + a host helper, not in-WASM. |
| Wall-clock deadline | 10s | Backstop for "spent fuel but stuck in a host call" cases. Implemented as a `tokio::time::timeout` around the `call()` future. |

All three are knobs on `HostPolicy` and surface to operators via the
existing `codeless config` channel. Crossing any cap → the call
returns `tool-error { code: "limit-exceeded", retryable: false }`
and the instance is dropped (not reused).

## Instance lifecycle

Per-call instantiation by default. Wasmtime cold-instance time is
sub-millisecond for typical plugin sizes; the simplicity of
"instance per call → drop after" outweighs the latency win of pooling.

```
PluginRegistry::dispatch(tool_id, args)
  → WasmPlugin::call(args)
      → engine.instantiate(component)        # fresh store, fresh fuel
      → bindings.call_tool_call(req)
      → drop(store)                          # everything goes
  → ToolResult
```

If profiling later shows instantiation is a measurable share of
tool-call latency, we add an instance pool. Don't pre-optimise.

**State across calls.** A plugin gets none, in-WASM. Plugin state
that needs to persist between calls lives in the plugin's SQLite
tables (item 6, `<plugin_id>_*` namespace) accessed through a host-
implemented WIT interface `codeless:db/kv@0.1.0` (v0.2, not v0.1).
In v0.1, stateful plugins use the builtin-Rust runtime flavour, not
WASM. This is a deliberate cliff — it keeps the v0.1 WASM surface
small enough to ship.

## Hot reload (dev only)

Production builds load `.wasm` files at startup and ignore changes.
A dev mode (`--plugins-watch`, gated by `Role::Standalone`) watches
the plugins dir; on a `.wasm` mtime change, the plugin's
`WasmPlugin` is dropped and reloaded, in-flight calls drained first.

The reload is **per-plugin**, not per-server. The persona, the
manifest, the SQLite migrations are not re-run on reload; only the
artefact is swapped. Manifest or migration changes still require a
full server restart. This matches the rubix Rhai-plugin reload story
([rubix EXTENSIONS.md § Evolution path](../../../rubix-workspace/rubix-agent/docs/design/extensions/EXTENSIONS.md))
without committing to a Rhai tier of our own.

Hot reload is not a hard requirement; it's a developer ergonomics
win. The substrate ships without it; we add it the first time a
plugin author asks.

## The authoring SDK — `codeless-plugin-sdk`

New crate, mobile-safe (no host dependencies), feature-gated for
flavour:

```toml
# codeless-plugin-sdk/Cargo.toml
[features]
default = ["builtin"]
builtin = []
wasm    = ["dep:wit-bindgen", "dep:wasi"]
# process = [...]    # reserved; lands with PLUGIN-PROCESS.md
```

Mutually exclusive — copy the `compile_error!` guard from rubix
`extensions-sdk/src/lib.rs` verbatim. Same shape, three flavours,
one authoring API.

The author writes:

```rust
use codeless_plugin_sdk::{tool, Tool, ToolCtx, ToolError};

#[derive(Tool)]
#[tool(id = "notes.append", tier = "write")]
struct NotesAppend;

impl tool::Behavior for NotesAppend {
    type Args = NotesAppendArgs;       // derives JsonSchema
    type Output = NotesAppendOutput;   // derives JsonSchema

    fn call(ctx: &ToolCtx, args: Self::Args) -> Result<Self::Output, ToolError> {
        let id = ctx.attachments().mint("note.md", args.body.as_bytes())?;
        Ok(NotesAppendOutput { attachment_id: id })
    }
}

codeless_plugin_sdk::register!(NotesAppend);
```

That source compiles **identically** to:

- a builtin Rust crate linked into `codeless-server` (`cargo build`,
  `feature = "builtin"`);
- a WASM component artefact (`cargo build --target wasm32-wasip2`,
  `feature = "wasm"`).

The `#[derive(Tool)]` macro is lifted from rubix's
`#[derive(NodeKind)]` (`extension-sdk/extensions-sdk-macros`),
rewritten to emit a `tool::Manifest` instead of a `KindManifest`.
The pattern carries; the body is new.

`register!` expands differently per feature:

- `builtin` — emits a `inventory::submit!` entry that
  `codeless-server` collects at startup.
- `wasm` — emits the WIT `export tool` glue (the `describe()` /
  `call()` exports) via `wit-bindgen`.

The author writes the same source either way. This is the load-
bearing claim of the substrate; if it stops being true, we have
failed.

## Manifest extension (item 6 addendum)

```toml
[plugin]
id        = "notes"
version   = "0.1.0"

[[runtimes]]
kind      = "builtin"
crate     = "codeless-plugin-notes"          # as today

# OR, equivalently:

[[runtimes]]
kind      = "wasm"
artefact  = "wasm/notes.wasm"

[runtimes.capabilities]
attachments = ["read", "write"]
fs          = []
http        = []
wall_clock  = false
```

A plugin may declare **at most one** active runtime per server
process. If a plugin ships both a builtin crate and a `.wasm`
artefact, codeless config picks one at server start
(`plugins.<id>.runtime = "wasm"`). Default: builtin if available,
else wasm. This lets a plugin migrate flavours without breaking
existing installs.

Strict-validate `kind`: only `"builtin"`, `"wasm"`, `"process"`
(reserved). Unknown → manifest parse error.

## Acceptance

The WASM flavour is done when:

1. The `notes` plugin from PLUGIN-SUBSTRATE item #0 builds with both
   `cargo build` (builtin) and `cargo build --target wasm32-wasip2`
   (WASM) from the same source.
2. `plugin_substrate_e2e::notes_plugin_loads_and_seeds_persona_
   addressable_by_thread` passes against the WASM artefact with the
   runtime flavour swapped via config — no test code change.
3. A new integration test
   `plugin_wasm_e2e::wasm_plugin_respects_fuel_cap` proves an
   intentionally-infinite-loop plugin returns
   `tool-error { code: "limit-exceeded" }` within 200ms.
4. A new integration test
   `plugin_wasm_e2e::wasm_plugin_cannot_open_host_file` proves a
   plugin with `[runtimes.capabilities] fs = []` cannot open `/etc/
   passwd` (or any host file).
5. The authoring docs in `codeless-plugin-sdk` show one `Tool` impl
   building two flavours, full stop.

## Open questions

- **OQ-WASM-1. Resolved 2026-05-18 (plugin-substrate-runtimes stage
  1): table lives in `codeless-tools` (mobile-safe), adapters live
  in their host-only crates (`codeless-plugin-host-wasm`, future
  `codeless-plugin-host-process`) gated behind Cargo features.**
  The table signature is `HashMap<ToolId, Box<dyn RuntimeAdapter>>`
  with no host-only types in the trait. The iOS/Android cargo-check
  matrix is the canary if a leak appears; the fallback ("table
  moves to a new mobile-safe `codeless-plugin-dispatch` crate")
  remains available without any code change today.
- **OQ-WASM-2. Resolved 2026-05-18 (plugin-substrate-runtimes stage
  1): commit the `wit-bindgen` output in-tree under
  `crates/codeless-tool-wit/`, regenerated by a documented
  `cargo xtask` invocation, never by `build.rs`.** A WIT change is
  an ABI change; the generated bindings diff is the load-bearing
  review artefact for that ABI change. Hiding it behind `build.rs`
  lets ABI drift land in a "merge cleanly" PR.
- **OQ-WASM-3.** Do WASM plugins get their own SQLite via
  `codeless:db/kv@0.1.0`, or do we say "WASM plugins are stateless,
  full stop, until v0.2"? **Lean: stateless in v0.1.** The kv
  interface is a real piece of design (transaction semantics, error
  shape, migration story) that we should not bolt on under time
  pressure. Plugins that need state ship as builtin until the WIT
  is designed. *Remains open beyond v0.1; not blocking this job.*
- **OQ-WASM-4. Resolved 2026-05-18 (plugin-substrate-runtimes stage
  1): refuse to hot-reload a plugin whose migration list has
  changed since the last load.** The host emits a structured error
  with code `migration-changed-restart-required` and the operator
  restarts. Migration replay against a running server is a separate
  piece of design (substrate item 6 / OQ-PS-5); bolting it on under
  the WASM banner couples two unrelated features.
- **OQ-WASM-5. Resolved 2026-05-18 (plugin-substrate-runtimes stage
  1): `HostPolicy` carries global defaults; the codeless config
  (`config.toml`) admits `[plugins.<id>]` overrides that may only
  lower the cap. The plugin manifest itself cannot set `fuel`,
  `memory_max_bytes`, or `deadline_ms`; the manifest parser rejects
  the fields, and a config override that exceeds the global default
  is a boot-time config-parse error.** The plugin author cannot
  enlarge their own sandbox; only the operator can, and only by
  editing the file the operator owns.

## Decisions locked

1. **WASI-p2 component model**, not core WASM. The SDK never speaks
   raw pack/leak/read\_slice.
2. **Default-deny capabilities.** No fs, no network, no wall clock,
   no env. Grants are explicit in the manifest and reviewed.
3. **Per-call instantiation.** No pooling until a profile demands
   it.
4. **One active runtime per plugin per server process.** Builtin
   and WASM cannot both be live for the same plugin id.
5. **Plugin authors never write raw FFI.** `#[derive(Tool)]` +
   `register!` macro are the only authoring surface. The macro
   emits builtin glue or WIT exports depending on Cargo feature.
6. **Reuse from rubix is per-file, not per-crate.** `wasm.rs` shape,
   the feature-flag guard, and the derive-macro pattern are ported
   with `// codeless-ported-from:` headers. `block-client`, `spi`,
   and the rubix graph SPI are not pulled in.
